01

What changed, and what didn't

The three-day plan spent its last day on tests, Instruments and polish. That day no longer exists, so those move into a four-hour block and get sharply narrower: four unit tests instead of twelve, two integration tests instead of a suite, one profiled optimisation with real numbers instead of three.

What does not move is the spine: UI process and monitoring process are genuinely separate, and the app survives the monitor dying. Everything else in this plan is negotiable. That is not.

Two things get added rather than cut, because they cost less than they look and they are what makes this stop being another Activity Monitor clone: Engineer Mode and the Xcode Workspace Inspector.

On the UI. You asked for sufficient, not showy — that is the right call and it is also what the role rewards. Budget the UI at roughly two of the fourteen hours. A clean SwiftUI dashboard with honest numbers beats an animated one, and Engineer Mode gives you visual interest that is earned by the architecture rather than applied on top of it.
02

The six sentences you say in the interview

Build the project backwards from these. If a feature does not serve one of them, it is a cut candidate.

Multi-process / XPC

"The UI never touches the kernel APIs. It holds an NSXPCConnection to an isolated service that does all sampling, and the service pushes snapshots back over a reverse proxy — so it's bidirectional, not request/response."

Reliability

"I kill the service from a button in the app. The connection invalidates, the UI shows degraded state, launchd relaunches the service on the next message, and metrics resume — typically inside two seconds."

Distributed notifications

"Lifecycle events go over DistributedNotificationCenter, not XPC. Streaming metrics and rare state changes have different delivery requirements, so they get different transports."

Sockets

"The service also listens on a Unix domain socket, so a CLI can query it without launching the GUI. Same data, second front door."

Systems knowledge

"Engineer Mode shows the real VM composition — wired, active, compressed, swapped — and the actual heap and stack region maps of my own two processes, read through mach_vm_region."

Instruments

"The directory walk was the hot path. Time Profiler showed it serialised on one queue; I moved to a bounded concurrent walk and cut a 3.4 GB scan from X to Y seconds. Numbers are in the README."

04

Scope, in three tiers

Ship items are the project. Stretch items happen only if you are ahead at a gate. Cut items are decided now, in daylight, so they do not reappear as a temptation at hour eleven.

XPC service with bidirectional connection

Ship

Embedded .xpc target in the app bundle. App exports a listener endpoint so the service can push snapshots; app calls in for commands. This single choice gives you multi-process, XPC, and a background service managed by launchd without writing a plist.

Connection state machine + kill/recover demo

Ship

States: disconnected → connecting → live → degraded → recovering. Driven by invalidationHandler and interruptionHandler. A developer button calls crash() on the service, which calls exit(1). This is your demo. Record the GIF of it.

Normal-mode dashboard

Ship

Three tiles (CPU, memory, disk), one CPU history chart off a fixed-size ring buffer, one top-processes table. Swift Charts, no custom drawing. Plus one AppKit NSStatusItem in the menu bar showing live CPU — cheap, and it makes "Cocoa/AppKit" true rather than aspirational.

Engineer Mode

Ship

A toggle that reveals the mechanism instead of the summary: live process topology with real PIDs and connection state, full VM composition bar, and real heap/stack/mapped-file region maps for MacEngine's own two processes. Detail below in section 05.

Xcode Workspace Inspector

Ship

Pick a .xcodeproj/.xcworkspace, get its true on-disk cost and the live memory footprint of the toolchain processes serving it. Detail below in section 06.

Distributed notifications for lifecycle

Ship

Five event names, posted by the service, consumed by the app, rendered as a live event log in Engineer Mode. About forty minutes of work and it ticks a named preferred skill.

Tests: 4 unit, 2 integration

Ship

Unit: CPU tick-delta normalisation, VM page-count composition, top-K selection, directory size roll-up. Integration: one XPC round-trip, one crash-and-recover. That is enough to talk about testing honestly.

One profiled optimisation with numbers

Ship

Time Profiler on the directory walk, fix the bottleneck, record before/after. Leaks clean. Screenshot both into Documentation/instruments.md. Do not skip this — it is explicitly named in the posting and it is the cheapest credibility in the whole plan.

Unix domain socket + macengine-cli

Stretch

Highest-value stretch item. Listener inside the service, a ~120-line CLI target. If tomorrow starts on schedule, build it. If not, the socket is the first thing you sacrifice — you still have two IPC mechanisms.

Tiny Objective-C bridge

Stretch

Twenty minutes: wrap the proc_listpids two-call dance in one small ObjC class with a bridging header. Makes "Swift and Objective-C" literally true and gives you a mixed-language build to discuss.

LaunchAgent / SMAppService / launchd plists

Cut

The embedded XPC service already is a launchd-managed background process. Writing a real agent means plists, install logic, signing and Login Items — hours of yak-shaving for a story you already have. Put it in README "future work".

App Sandbox, hardened runtime, notarisation

Cut

Sandbox blocks distributed-notification userInfo, complicates socket paths, and fights the DerivedData reads. Turn it off, sign to run locally, and say so in the README as a deliberate scoping decision for a local dev tool.

Mach ports, persistence, settings, animation

Cut

Mach ports add nothing you cannot already claim via XPC (which is built on them — that is your answer if asked). No Core Data, no preferences window, no onboarding, no transitions.

Anything about the app being built

Cut

Per your own scoping call, and it is the right one: MacEngine measures the project and the toolchain, never the built product's runtime. Instruments owns that and owns it better. Saying this out loud in the README reads as judgement, not as a gap.

05

Engineer Mode

Your instinct is right, with one adjustment. Drawing generic stack/heap textbook diagrams would be decoration, and an interviewer will spot it in one question. Instead, Engineer Mode shows this application's real mechanism — which happens to be a genuine OS-concepts tour, because the thing being explained really is IPC and virtual memory.

The adjustment is where the region maps come from. You can read full VM region maps for your own tasks without any privileges. Reading another process's regions needs task_for_pid, which means root or a debugger entitlement. So: deep region view for MacEngine's own app and service processes, footprint-level numbers for everyone else. That boundary is itself a good thing to be able to explain.

Four panels

  • Process topology — the section 03 diagram, live: real PIDs, real connection state, message counts, and the last event. Watch it re-draw when you kill the service.
  • Virtual memory composition — a stacked bar of wired / active / inactive / speculative / compressed / free from vm_statistics64, plus swap in-use from vm.swapusage and the pressure level from kern.memorystatus_vm_pressure_level. Labelled with what each state actually means.
  • Address space map — for the app and the service: heap, stack, __TEXT, mapped files, and shared regions, walked via mach_vm_region_recurse. This is your honest stack/heap diagram, drawn from live data.
  • Sampling pipeline — collect → encode → XPC transit → decode → render, with measured microseconds per stage. It is where your Instruments story becomes visible in the product.

Implementation shortcut

Do not build two view hierarchies. Engineer Mode is one @AppStorage boolean; each dashboard section reads it and renders either the summary or the mechanism. Shared view models, one extra panel column. Budget 90 minutes, not a day.

What it buys you

Visual interest without visual effort
A reason the architecture is visible to a non-reader of your code
Direct OS-concept vocabulary in the demo: paging, compression, address spaces, IPC lifetime
Do not promise per-process heap maps for arbitrary PIDs
Do not draw a CPU pipeline or cache hierarchy you cannot measure
06

Xcode Workspace Inspector

This is the feature that makes the project yours rather than a tutorial. It answers a question every macOS/iOS developer has actually asked — where did my disk go, and what is Xcode doing to my machine right now — and it does it without pretending to be Instruments.

The disk half — measured on your machine, just now

These are real numbers from this Mac. They are also why the feature lands: 12 GB of developer state, and most of it is invisible in Finder.

LocationWhat it isSize nowWeight
CoreSimulator/DevicesSimulator runtimes and per-device data6.0 GB
DerivedData/<Project>-<hash>Build products, index store, logs, per project1.8 GB
DerivedData/ModuleCache.noindexPrecompiled module cache, shared1.4 GB
Caches/org.swift.swiftpmResolved SwiftPM package checkouts484 MB
DerivedData/SymbolCache.noindexShared symbol cache44 MB
~/Library/DeveloperTotal developer footprint12 GB

Archives and iOS DeviceSupport are empty here — still enumerate them, they are the two that explode on other people's machines.

The one trick you need. A DerivedData folder is named <ProjectName>-<28-char hash> and the hash is not reproducible from the path. Do not try to compute it. Every DerivedData subfolder contains an info.plist with a WorkspacePath key — read those, match the one pointing at the project the user picked. Ten minutes, exact answer.

The memory half

What you can measure, unprivileged

Live footprint of the toolchain process family — Xcode, SourceKitService, swift-frontend, clang, XCBBuildService, simd/simulator processes, and any python/MLX job — grouped and summed, via proc_pid_rusage and ri_phys_footprint
System-wide pressure, compression ratio and swap growth while a heavy job runs
A "watch" mode: start recording, run your build or your MLX training, stop — get peak footprint, peak pressure, swap delta, and disk delta over that window
Per-process heap breakdowns for Xcode (needs task_for_pid)
Allocation stack traces or leak detection in other processes

Why the watch mode matters

This is the part with no good existing tool. Activity Monitor shows you now; Instruments profiles one process you launched. Nothing gives a developer a labelled recording of "what did this build, or this MLX training run, cost my machine in memory, swap and disk."

It is also the cheapest feature in the section: you already have the sampler and the ring buffer. Watch mode is a start marker, a stop marker, and max/delta reduction over the window. Under an hour.

Say this in the README, in one line. "MacEngine deliberately does not profile the app you are building — Instruments does that better. It profiles the project and the toolchain: what your workspace costs on disk, and what your Mac pays in memory while the toolchain works." Scoping stated confidently reads as engineering judgement.

Decisions made in advance

Each of these is a place where the default choice costs an hour or more. Make them now so you never stop to think about them.

DecisionTake thisBecause
Swift language modeSWIFT_VERSION = 5Xcode 26 defaults new targets to Swift 6. Strict concurrency across an XPC boundary is a genuine time sink and buys you nothing for this demo.
Background serviceEmbedded .xpc targetlaunchd already starts it on demand and relaunches it after a crash. You get the background-service story for free; a real LaunchAgent costs hours.

Metric deliveryService pushesApp exports a listener endpoint; service calls into it. Makes the connection genuinely bidirectional, which is the stronger interview answer.
SandboxOffUnblocks distributed-notification userInfo, /tmp sockets and DerivedData reads in one move. Document it as a deliberate choice for a local developer tool.

ChartsSwift ChartsBuilt in, macOS 13+, and you are on 26.5. Zero custom drawing.
PersistenceNoneRing buffer in memory. History resets on relaunch and nobody will ask.
09

Landmines

  • Distributed notifications need a run loop. If the service posts from a detached thread with no run loop and nothing arrives, that is why. Post from the main queue.
  • Under the sandbox, distributed-notification userInfo is stripped. You are unsandboxed, so it works — but keep event payloads tiny anyway so the mechanism stays defensible.
  • The XPC service is on-demand. It will not be running until the first message. Your "service down" state and your first connection look identical; make the state machine treat them the same and the recovery path is the same code as the startup path. That is a feature, not a bug — mention it.
  • Integration tests need the host app. The .xpc is embedded in the app bundle, so the test bundle must be hosted by the app to reach it. Set the test host, or the connection will just fail with an obscure error.
  • CPU percentages come from deltas, not absolutes. host_statistics64 returns cumulative ticks. Two samples and a subtraction. Getting this wrong produces a number that looks plausible and is not — and it is exactly the kind of thing an interviewer probes.
  • Use allocated size, not file size, for the disk walk, or your totals will not match Finder and someone will notice.
  • Do not walk the whole home directory. Scope every scan to a known developer path. An accidental full-volume enumeration will hang the demo.
