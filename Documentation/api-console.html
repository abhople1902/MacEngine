How it fits together

The index above is sorted by area, which deliberately says nothing about order or dependency. This is the other half of the reference: which layer each area belongs to, what each one is allowed to know, and the exact path a number takes from a kernel counter to a pixel.

Three layers and two straps

Eleven areas, but they are not eleven peers. Three of them stack; the rest either cut across the stack or surround it.

layer 1 · bottommach · proc
The only families that actually measure anything. host_statistics answers “what is the machine doing”, proc_pidinfo answers “which process is doing it”, and neither is meaningful from a single call — both return cumulative counters, so a rate only exists between two samples. Nothing above this layer talks to the kernel.
layer 2 · middlexpc · ipc · lifecycle
Everything that exists only because MacEngine is two processes instead of one. NSXPCConnection carries the payload, launchd decides when the second process exists at all, and DistributedNotificationCenter carries the human-readable event stream that has to survive either side dying.
layer 3 · topappkit/ui
The only layer with no measurement code in it whatsoever. It renders whatever the last decoded snapshot said and never blocks on the service — which is why a crash below it changes the status pill rather than blanking the window.
strap · both sidesconcurrency · data structures
Cross-cutting, because both processes need it. Actors serialise mutable sampler state so no lock is required; BoundedTopK reduces ~600 processes to 5 before anything is encoded, so payload size does not track process count; RingBuffer caps chart history at 120 samples so an all-day run has a flat memory profile.
strap · a gate, not a layersecurity
One decision reaching in two directions. App Sandbox blocks proc_pidinfo for foreign processes (layer 1) and strips userInfo from distributed notifications (layer 2), so turning it off was one call with two consequences — and task_for_pid is the boundary that keeps region maps limited to MacEngine’s own two processes.
enclosure · around all of ittesting · instruments
Aimed at every layer independently: samplers unit-tested without a connection, the XPC contract tested across a real process boundary, and Time Profiler pointed at the sampling loop. The one thing they proved that reading the code did not: a synchronous walk that never yields will occupy every thread in the cooperative pool and starve the task trying to cancel it.

One tick, end to end

The steady state, once a second, in the order it actually happens. Time runs downward; each horizontal arrow crosses a real process boundary.

  1. XPCMetricsProvider.connect()Builds the NSXPCConnection, sets remoteObjectInterface and exportedObject, and resumes it. No second process exists yet — launchd starts one on the first message, not on resume().
  2. startMonitoring(interval: 1.0)The first real message, and therefore the thing that actually launches the service. Its withReply block is the only acknowledgement available.
  3. MetricsCollector — Task loop startsOne actor owns all four samplers, so their mutable previous-reading state needs no lock and two samples cannot interleave.
  4. mach_host_self() → host_statistics(HOST_CPU_LOAD_INFO)Cumulative ticks since boot, differenced against the previous reading with &- so a counter wrap is a slightly wrong sample rather than a trap.
  5. host_statistics64(HOST_VM_INFO64)Page counts read through withMemoryRebound, then multiplied by vm_kernel_page_size — not 4096, which is wrong by 4× on Apple Silicon.
  6. proc_listallpids → proc_pidinfo(PROC_PIDTASKINFO)Per-process CPU time and resident size. This is the call App Sandbox would have refused for every process but our own.
  7. BoundedTopK.insert(_:)~600 processes reduced to 5 in a single pass with a min-heap: O(n log k) time, O(k) space, and a payload whose size does not grow with the process table.
  8. JSONEncoder().encode(snapshot)The payload crosses as encoded Codable inside Data, so neither side has to maintain an NSSecureCoding class whitelist.
  9. didProduceSnapshot(_:)One-way across the boundary. The service does not wait for the app, which is what keeps the sample interval honest.
  10. JSONDecoder → provider actorStores latest, bumps pushesReceived. If the newest snapshot is older than max(interval × 2, 1 s), the provider falls back to the pull path instead of showing a lie.
  11. RingBuffer(capacity: 120) → DashboardViewFixed-capacity history on the @MainActor view model, then the chart, the tiles and the NSStatusItem redraw. Memory is flat whether the app has run a minute or a day.

What happens when it breaks

The recovery path is the reason the split exists, so it is worth being able to draw from memory.

The other shape on the same connection

Not every job fits request/reply. A full workspace walk takes tens of seconds, so startWorkspaceScan(path:) replies as soon as the job is accepted and everything afterwards arrives on the client interface as ScanUpdate values through didUpdateScan(_:) — one .started, many .progress, then exactly one .finished or .cancelled. Two consequences worth naming out loud: the reply block means “queued”, not “done”; and the client channel has to be captured with the request rather than when the connection is accepted, because a one-shot .started emitted before the channel is attached is dropped in total silence. That was a real bug, and it only showed up on the one-shot message — a 1 Hz stream hides it completely.

the sixty-second version

MacEngine is two processes. The one you see is a SwiftUI app that contains no measurement code at all; the one you don’t is an XPC service, started by launchd, that owns every Mach and libproc call. Once a second the service’s collector actor samples CPU ticks, VM page counts, disk and per-process task info, reduces roughly six hundred processes to the top five with a bounded min-heap, encodes the result as JSON and pushes it one way across an NSXPCConnection. The app decodes it, appends it to a 120-sample ring buffer and draws. If the service dies, interruptionHandler fires, the app records the reason once and reconnects — launchd restarts the service on the next message, and the window never blanks, because the last snapshot is still on screen and a pull path covers the gap. The split is the whole point: a fault in the sampling code cannot take down the UI, and the sandbox decision only has to be made for the process that actually needs the access.
